# 第二阶段：服务重启后恢复牌局

## 范围与部署条件

同一个 Redis 数据库上只运行一个游戏服务实例，升级时先停止旧进程再启动新进程。二期恢复已经发牌、尚在保留期内的牌局，以及短期终局结果；未开局的等待房间、匹配队列不恢复。游客身份验证仍使用一期的 Redis 凭据和 HttpOnly Cookie。旧版简化 `room:*` 数据不作为权威状态，升级前尚未生成二期快照的局不能恢复。

使用随代码更新的 Compose 配置：Redis 数据卷持久化，`appendonly yes`、`appendfsync always`。自行部署 Redis 时也必须设置这两项，并确认写入目录及磁盘可用。默认的 `appendfsync everysec` 可能在 Redis 崩溃时丢失最近约一秒已经确认的动作，不满足本阶段的确认保证。服务进程崩溃和 Redis 进程崩溃可恢复；磁盘/数据卷丢失需要恢复备份，备份之后的数据无法补回。

Web 和终端需要同步更新。出牌/不出新增 `turn_token`，旧终端缺少令牌的动作会被拒绝；新版终端仍使用原有持久游客凭据。浏览器不接触身份凭据，也不会收到其他人的私有快照。

## 权威快照与确认顺序

`game:v2:<game_id>` 保存 schema version、稳定牌局 ID、递增 revision、保存时间、到期时间和完整状态。稳定牌局 ID 跨无人叫地主重新发牌保持不变，`deal_id` 标识每次发牌。快照包含：

- 玩家 ID、昵称、座位、真人/机器人标记、角色、离线状态和所有精确手牌（含花色与颜色）。
- 底牌、牌堆、叫抢参与状态及历史、当前候选地主、倍数、炸弹及春天计算所需计数。
- 完整公开出牌/不出记录、上一手牌型、当前行动者、回合序号、叫牌及出牌令牌。
- 发牌时间、回合绝对截止时间、离线等待截止时间、暂停时剩余时长、离线保留及终局到期时间。
- 终局展示结果及需要写入排行榜的真人结算结果。

有效动作和阶段变化在牌局锁内计算候选状态，暂存消息与释放席位等副作用，再同步提交 Redis。只有提交成功后才广播出牌、叫抢、发牌、回合和终局消息，或允许玩家离开已结束的牌局。`game_start` 只表示房间已进入准备开局，首次带手牌的 `deal_cards` 才确认发牌已经持久化。非法动作不更新 revision。

Redis Lua 比较前一 revision 后写入。完全相同的候选 revision 和内容可重试成功；旧 revision 或同 revision 的不同内容会失败，不能覆盖较新的状态。写入出错或响应中断时，保留同一候选状态、停止推进该局，不广播成功，不接受后续动作；每秒重试同一份候选。版本冲突则停止自动重试并记录日志，需检查是否运行了第二实例或混用了备份。Redis 暂时不可用不会降级为只在内存继续游戏。每次提交等待最多两秒，等待期间的新离线/上线事件排队，在候选确认后继续持久化。重连阶段保存失败时保留玩家的牌局关联并关闭失败连接，由客户端现有自动重连流程重新完成房间替换和快照接收。同步提交和 `appendfsync always` 会增加动作延迟，容量规划应使用实际存储设备压测。

如果 Redis 已写成功而服务在广播前崩溃，恢复时以 Redis 为准。客户端应重连读取快照；旧叫牌令牌、出牌令牌和机器人回合序号不能再次推进牌局。重复请求会被拒绝，而不会重复广播或重复出牌。写入等待仍保留原绝对截止时间，恢复存储后若截止时间已过，沿用下述单次超时策略。

## 启动与停机时间

HTTP/WebSocket 开放前加载并校验所有二期快照。版本不支持、牌数/牌面不合法、座位无效或同一真人属于多个有效局时，启动失败，避免静默丢局。启动恢复入口在同一进程内只执行一次。

真人重建为离线占位，通过原凭据重连后替换占位；机器人保留原 ID 和昵称，重放公开叫抢/出牌历史并恢复自己的手牌，再接回决策引擎。服务启动时会重建玩家到活动牌局或短期结算的关联，活动局优先。旧房间或占位客户端释放席位时，仅在共享会话仍指向该原房间时清除关联，不能清空玩家的新活动局。

停机期间按墙上时钟计时，不重新发牌，不重新随机选择行动者，不重置已保存的截止时间。截止时间尚未到时恢复剩余时间；已过期时仅执行当前阶段的一次超时动作，然后为下一回合设置正常时限，不快速补演停机期间所有回合。原本暂停的离线回合保留剩余时长及离线等待截止时间。

重启后所有真人视为离线。若此前已有全员离线时间，继续沿用；否则保守地从最近一次持久化活动时间计算全员离线保留期。超出保留期的局不恢复。恢复的牌局继续使用原快照中的保留配置。终局仍只展示到原结算截止时间，但其尚未完成的战绩补写不会随房间过期删除。

## 结算与备份一致性

终局快照与 `game:pending-results` 有序待写记录在同一个 Lua 操作中提交。后台按完成顺序处理，每位玩家较新的结果不能越过该玩家失败的旧结果；不相关玩家仍可继续处理。统计、排行榜与 `result:recorded:<game_id>:<player_id>` 标记在同一个 Redis 事务里更新。标记不设 24 小时过期，避免长时间停机或重复恢复后重新计分。成功后再确认待写记录；确认前崩溃也不会重复计分。

二期不再依靠十分钟的内存重试窗口保存战绩。持久待写结果保留到写入成功；房间展示过期和统计写入完成后才可清理权威终局快照。应监控 Redis 容量、持久化错误及长期滞留的待写记录。

备份必须是同一时点的整个 Redis 数据库，包含身份、游戏、统计、排行榜、待写记录与去重标记。不要只恢复游戏键或混合不同时间的备份。

```sh
# 密码通过 REDISCLI_AUTH 环境变量传入；目标目录需预先创建。
bash scripts/backup-redis.sh /secure/backups/ddz-2026-11-09.rdb -h 127.0.0.1 -p 6379
sha256sum -c /secure/backups/ddz-2026-11-09.rdb.sha256
```

脚本通过 Redis 的复制快照导出一致 RDB，用临时文件完成后再移动，不覆盖已有备份，文件权限限制为当前用户。备份含精确手牌及持久身份，应存放在受控、独立于运行数据卷的位置。

恢复步骤（先在隔离环境演练）：

1. 停止游戏服务及目标 Redis，保留原数据卷，不在运行中的数据库上覆盖文件。
2. 校验备份校验和，将 RDB 复制到一个新的空数据目录，命名为 `dump.rdb`，修正 Redis 进程所需的所有权。不要把旧 AOF 一并复制过来。
3. Redis 用这个目录以 `appendonly no` 启动并加载 RDB；先不开放游戏服务。
4. 执行 `CONFIG SET appendfsync always`、`CONFIG SET appendonly yes`，等待 `INFO persistence` 中 `aof_rewrite_in_progress:0` 且 `aof_last_bgrewrite_status:ok`，确认 `aof_last_write_status:ok`。
5. 将启动配置固定为 `appendonly yes`、`appendfsync always`，重启 Redis 验证新 AOF，然后启动一个游戏服务实例。检查恢复日志、原身份续局及结算次数。

## 自动验证

```sh
go test -race -tags ci ./...
# redis-server 与 redis-cli 在 PATH；测试使用临时目录和独立本地端口。
DDZ_REDIS_INTEGRATION=1 go test -race -tags ci ./internal/server \
  -run TestProcessCrashRedisRestartAndBackupRecovery -count=1 -v
make lint
cd web && npm test && npm run build
```

CI 安装 Redis 并启用真实进程测试。测试覆盖服务 SIGKILL、Redis SIGKILL/AOF 重启、RDB 备份导出与异地目录恢复、恢复后重新生成 AOF、精确手牌与牌局 ID 一致性。Go 测试另覆盖阶段快照往返、旧写覆盖、重复动作、写入前失败、提交后丢响应、单次停机超时、机器人状态恢复，以及终局和统计重复恢复。
